# 10XSC trial allowance

The trial has three simultaneous limits: a one-time maximum of **100 successful text-only guided turns per eligible account**, a USD cost allowance per account, and a total event cost budget. Usage stops at whichever limit is reached first. These are app-managed API cost estimates, not cash, prepaid OpenAI balances or a guarantee that every account can complete 100 turns. No monetary amounts or model rates are selected automatically.

## Activation (required, intentionally off by default)

1. Deploy the latest app code, then run [supabase/credits.sql](../supabase/credits.sql) in Supabase SQL Editor. The same SQL is available at `/credits.sql` on the deployed site. Run the whole script; it is transactional and rerunnable without resetting grants or balances. It creates only the wallet/control tables and server-only functions, leaving existing saved cases intact.
2. Keep `SOLVE_WORKSHOP_ENABLED=true`, the existing Supabase settings, `SOLVE_WORKSHOP_ADMIN_CODE` and `OPENAI_API_KEY` in Production. Shared trial mode uses the tested, pinned model **gpt-4.1-mini-2025-04-14**, independently of personal provider connections. Changing that model needs a reviewed code/price update, not merely an environment variable change.
3. Open `/#workshop-admin`, enter the facilitator code, and find **Control trial usage → Load trial controls**. The initial configuration is disabled, approval-only, with zero budgets and zero prices. Missing database setup is reported without falling back to unmetered organizer-key usage while workshop controls are enabled.
4. Verify the model's current input/output USD prices per million tokens in OpenAI's pricing/account pages. Enter those rates, the event budget and the allowance per account. Do not confuse **US$5 for the entire test pool** with **US$5 for each participant**. No current prices were verified or hardcoded by this change. Confirm the price acknowledgement before enabling trials.
5. Under **Approve existing participant accounts**, enter the emails of trusted, already-registered participants (up to 300). Approving again never resets the same account's grant. If email confirmation is disabled, independently match the account to the real participant before approval. Approving an email by itself does not prove the registrant owns that address. The alternative “All signed-in accounts” policy explicitly includes unverified addresses and is susceptible to multiple-account abuse; it is not the default.
6. For first testing, approve only the organizer and a few trusted accounts, with a modest total pool and per-account allowance chosen by the organizer. Enable trial usage, then release **OS mode** using the existing workshop controls. AI remains blocked during Workshop, regardless of balance, personal key or access code.
7. Participants sign in and use **Trial balance** to check eligibility and limits. With no personal key selected, guided **Continue · trial turn** uses the 10XSC server key. No participant should paste the organizer's key into the app. Existing draft answers can be retried after activation. Personal API connections remain a separate option, billed by their selected provider.

## Exactly what is metered

- One successfully processed `/api/guide` response uses one turn and its conservatively estimated API cost. The response contains a single next question and the existing structured SOLVE fields. Larger histories remain stored/exportable; AI receives the already bounded case context. Trial outputs are capped at 1,800 tokens, with a 25-second provider timeout.
- Trial requests are text-only. Uploaded files and website/business extraction through `/api/assist` are refused for shared trial access **before** a provider or website request. Those actions still work with a participant's personal API connection. Manual worksheets, storage/sync and local PDF downloads remain free.
- JWTs are checked with Supabase Auth. The server chooses the wallet owner from the verified identity, never from a participant-supplied ID. Browser balances are informational, never authoritative. Refreshing an expired token uses the app's existing account refresh flow.
- PostgreSQL transactions reserve a participant turn plus account/event budget before calling OpenAI. There is at most one in-flight trial call per account and six accepted attempts per minute. Budget rows and wallet rows are locked in a consistent order, so simultaneous requests cannot reserve the same balance twice.
- The initial cost reservation uses an intentionally generous input-token upper bound (serialized request UTF-8 size plus overhead) and the maximum output allowance. This can prevent a long turn even when its eventual actual cost might have been lower. Use a shorter update or a personal connection; do not promise 100 turns irrespective of budget.
- When OpenAI returns the expected model and valid usage, the reservation is reduced to the supplied token counts multiplied by the facilitator's configured rates. Cached input is conservatively treated as uncached input. Figures shown are therefore cost estimates, not a reconciliation of OpenAI's invoice.
- Failed responses return the participant's turn and account allowance, but the event budget covers any provider usage already incurred. If the response/usage is unknown, the full reservation is treated as possible event cost and shared usage pauses for review. A facilitator can inspect the OpenAI Usage dashboard, reload controls and deliberately re-enable after resolving the problem.
- These limits cover this app's shared trials only. Admin diagnostics, personal keys, other applications using the organizer key, price changes or incorrect manually configured rates are outside the pool. OpenAI project budget notifications are not a hard provider spending cap. Keep a small provider balance/auto-recharge policy appropriate to the risk and verify rates before launch.

## Retries and interrupted requests

Every guided request has a stable UUID saved with the draft. The server verifies ownership and a SHA-256 fingerprint of the meaningful context/message. Browser-only fingerprints are not trusted for authorization. Date/timezone metadata does not create a duplicate billable request when retrying the same draft after midnight.

A successful repeated ID replays the recorded structured result without another provider call or another turn charge. A pending repeated ID asks the client to wait. A definitively failed response clears the browser's tracked ID, allowing an explicit new attempt. Changed answers get new IDs. No provider calls are automatically retried. Reloading/closing the page can preserve the pending draft and ID through the existing account/device save flow.

If a server crashes after reservation, a later balance check or request releases attempts older than ten minutes. The participant gets the turn back once, while possible event cost remains charged conservatively. No late success can settle that released attempt again. If provider success happened but wallet confirmation was lost, the client is told to retry the same answer rather than blindly sending a duplicate.

Do not manually reset balance rows or delete pending users/ledger rows to grant more trials. The request ledger stores private structured responses for retry replay and aggregate accounting. Plan a deliberate retention/export policy before pruning it; pruning IDs also removes their idempotency history. Existing access-code behavior is retained only when global workshop controls are disabled, so keep controls enabled for the metered event.

## Validation and remaining rollout work

The tests run the migration and accounting functions against embedded PostgreSQL (PGlite), including repeated grants, simultaneous requests, exhausted 100-turn allowances, event/account budget holds, failure refunds, stale attempts and denied public privileges. API tests combine that real ledger with mocked Auth/OpenAI services to exercise verified ownership, structured answers and retry replay. Browser checks cover signed-in headers, a paused request, admin configuration/approval, a successful retry, the updated balance and phone/desktop layout.

Production SQL activation, live Supabase/OpenAI accounting, current price verification, representative full-case cost measurement and a 200–300 participant load test still need an organizer-led rehearsal. No live paid requests or production migrations were run by this development environment.

**Stripe payment packages, checkout and automatic paid credit fulfilment remain unimplemented and disabled.** There is no purchase entitlement or cash balance in this migration. A paid wallet should use a separately reviewed, idempotent Stripe webhook and pricing model rather than treating a checkout redirect as proof of payment.
